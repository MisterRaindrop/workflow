# wk v2 整体设计

只讲结构，不讲实现。细节与实测依据见 [lxd-slot.md](lxd-slot.md)。

---

## 1. 这个工具是什么

**wk 是 LXD 容器的管理器。** 造容器、开关容器、看容器 —— 就这三件事。

容器里有独立的 Docker daemon，所以 CI 那些写死的固定名字（`shared-ci-net`、`mysql`、
`services-hive`）可以在多个容器里同时存在，互不干扰。

**代码不属于这个工具的职责。** 代码就是 host 上一个普通目录，你自己 `git clone` 一份，
`wk` 只负责把它绑进容器、把权限弄对。换代码就是再绑一次。

跟 git worktree 没有任何关系。

---

## 2. 为什么隔离要放在 Docker daemon 这一层

冲突源是 CI 脚本里写死的名字，改是改不完的，所以隔离边界必须下沉到 daemon：

```
❌ 共用宿主机的 Docker daemon
        任务 A ─┐
        任务 B ─┼─▶ 同一个 docker ──▶ 争抢同一个 shared-ci-net / mysql
        任务 C ─┘

✅ 每个容器一个 Docker daemon
        lxslot1 ──▶ docker ──▶ shared-ci-net / mysql / hive  ┐
        lxslot2 ──▶ docker ──▶ shared-ci-net / mysql / hive  ├ 同名，互不可见
        lxslot3 ──▶ docker ──▶ shared-ci-net / mysql / hive  ┘
```

LXD 系统容器 + nesting 提供的正是这个边界。这是整个方案存在的唯一理由。

---

## 3. 只有两个对象

```
容器（长期，造一次几十分钟，反复复用）
  └── 绑一个代码目录（短期，随时换）
```

| | 是什么 | 活多久 | 谁准备 |
|---|---|---|---|
| **容器** | Docker daemon + 工具 + 认证 + 预热镜像 | 长期，跨任务复用 | `wk new`，一次性 |
| **代码目录** | host 上一个普通目录 | 想删就删 | **你自己 clone** |

没有「任务」这个对象。**容器就是工作单元** —— 要同时干三件事，就开三个容器。
「这个容器现在在干什么」由「它绑了哪个目录 + 一句备注」表达，不需要额外抽象。

关键：**容器不持有代码，代码不感知容器**。换代码不用碰容器，换容器代码不受影响。

---

## 4. 分层

```
┌───────────────────────────────────────┐
│ CLI          wk                        │  单文件 bash，在 host 上执行
├───────────────────────────────────────┤
│ 能力层       对一个容器做事             │  造 / 绑代码 / 起服务 / 认证 / 监控
├───────────────────────────────────────┤
│ 驱动层       lxc · docker · git        │
└───────────────────────────────────────┘
```

现有 `lxd-slot-demo.sh` 就是能力层，直接继承。

而现有 `slotctl.sh` 的主体 —— task 状态机、状态文件、slot 分配调度 —— **在这版设计里不需要了**
（原因见 §5）。这砍掉了要维护的大部分复杂度，连带消灭了并发分配撞车的问题。

---

## 5. 状态：全部存在 LXD 里，没有外部状态文件

这是这版设计最大的简化。原来要维护 `<task>.env` 状态文件、要处理并发写、要防状态漂移。
现在全都不需要 —— 因为**要存的东西 LXD 本来就存着**：

| 想知道 | 从哪来 |
|---|---|
| 容器状态（跑着 / 冻着 / 停着） | `lxc list` |
| 绑了哪个代码目录 | 容器的 disk device 配置 |
| 备注、最后访问时间、内存峰值 | 容器的 `user.wk.*` 自定义配置项 |
| 服务是否健康 | 容器内 `docker ps` |
| 当前内存占用 | 容器的 cgroup |

原则从「能推导的不存」升级为 **「什么都不自己存」**。
没有第二份真相，就没有漂移，也没有并发写。

## 6. 容器状态机

就是 LXD 原生的三个状态，没有自造状态：

```
        wk new
          │
          ▼
      ┌────────┐   4h 无访问（自动）   ┌────────┐
      │RUNNING │ ────────────────────▶ │ FROZEN │   进程冻在内存里
      │        │ ◀──────────────────── │        │   秒级恢复
      └────────┘   任何访问（自动）     └────────┘
          │  ▲
   wk stop│  │wk start
          ▼  │
      ┌────────┐
      │STOPPED │   释放内存，容器内进程丢失
      └────────┘
          │
          │ wk rm
          ▼
       (删除)
```

设计要点：

- **冻结优先于关停**。回收资源不该让你丢掉跑一半的编译和 tmux 会话。
  自动回收只做冻结（省 CPU，不省内存），关停是显式动作。
- **恢复是隐式的**。任何访问自动解冻，不需要你先想起来「它是不是睡着了」。
- 代码绑定与容器状态**正交** —— 冻结/关停都不动绑定关系。

## 7. 网络：容器怎么出网

这是实践中摩擦最多的一块，值得单独讲清楚。

容器挂在 `lxdbr0` 上，而 host 的 `FORWARD` 策略是 `DROP` —— 所以**容器默认什么都访问不到**。
出网靠两条显式放行的通道：

```
容器 ──┬── 代理通道 ──▶ HTTP(S) 代理 ──▶ 外网 / 部分内网
       │     放行 lxdbr0 ↔ 代理:port
       │
       └── 直连通道 ──▶ WK_DIRECT_HOSTS 里列出的地址
             放行 lxdbr0 ↔ 该地址（不经代理）
```

**为什么两条都要**：代理只对「读 `HTTP_PROXY` 环境变量」的程序有效。
构建工具里有相当一部分不读它 —— Maven 只认 JVM 系统属性，某些镜像还会在 profile 里
无条件 `export MAVEN_OPTS` 把外部注入覆盖掉。对这类工具，唯一可行的是让它直连。
所以 `WK_DIRECT_HOSTS` 存在，用来精确放行内网仓库这类必须可达的地址。

**代理要送进三个地方**，缺一不可：

| 层 | 怎么送 | 不送的后果 |
|---|---|---|
| 容器自身 | LXD `environment.*` 配置 | 容器里的 apt / curl 出不去 |
| 容器内的 Docker daemon | systemd drop-in | `docker pull` 出不去 |
| **daemon 启动的每个容器** | `~/.docker/config.json` 的 `proxies` | **构建容器出不去** |

第三层最容易漏。项目的构建规则通常不会把代理变量传进 `docker run`，
而 Docker CLI 的 `proxies` 配置会自动为每个容器注入 —— 于是不必修改项目的 Makefile。

**规则不持久，所以每次都断言**：`iptables` 规则在 host 重启后全部消失，
而 LXD 会自动把容器拉回 RUNNING —— 容器在跑，不代表规则还在。
因此 `ensure_egress()` 挂在 **每一条会用到网络的路径**上（不只是启动容器时），
每次执行都用 `iptables -C` 幂等地检查并补齐。`wk doctor` 负责报告，`--fix` 负责修复。

**代理本身不可靠**：观察到间歇性故障（几分钟自愈）和对部分境外目标的稳定失败。
因此 apt 带 5 次重试；判断代理是否真的坏了，要**在 host 上直接测**，
不能只看容器内的报错 —— 容器内失败可能只是规则丢了。

## 8. 监控

这是工具的第三件核心事，全自动，不用敲命令：

```
持续采样  ──▶ 每个容器的真实内存占用（anon，不是含缓存的那个数）
              记录峰值，写进容器自己的 user.wk.* 配置

idle 跟踪 ──▶ 4h 无访问 → 自动冻结
              长期无访问 → 在 wk ls 里标出来，让你决定

容量守卫 ──▶ 造新容器前估算：现有容器峰值之和 + 新容器预估 vs host 可用内存
              不够就打 WARNING 劝退，并列出依据（谁占了多少、还剩多少）
```

一个关键坑：容器报出来的内存数字含 page cache，会**高估约 9 倍**
（实测 lxslot1 显示 13.3G，真实占用只有 1.4G）。采样必须取 anon，否则会得出
「31G 内存只能开两个容器」这种错结论，白白劝退。

## 9. 命令

全是容器动词，日常只用前两条：

```
日常
  wk ls                    看所有容器：状态 / 闲多久 / 内存 / 绑了哪份代码 / 备注
  wk enter <name>          进去（冻结的自动解冻，停了的自动启动）

换代码
  wk bind <name> <dir>     把一个代码目录绑进容器（顺带起项目服务）

开关
  wk pause <name>          冻结（进程留在内存，秒恢复）
  wk stop  <name>          关停（释放内存）
  wk start <name>          启动

基建（很少动）
  wk new [name]            造一个容器 —— 一次性，几十分钟
  wk rm  <name>            删容器
  wk doctor                体检：LXD / 代理 / 内存 / 权限
  wk auth                  host 上重新登录后，把认证同步进容器
```

不在主帮助里、排障用：`wk exec <name> <cmd>`（不进去跑一条）、`wk up|down <name>`（单独起停服务）、
`wk smoke <name>`（服务自检）。

## 10. 典型用法

**第一次用这台机器**（一次性，慢在这里）

```bash
wk doctor        # 体检
wk new           # 造容器：装 Docker、灌镜像、播认证 —— 几十分钟
```

**日常**

```bash
wk ls                              # 看一眼谁在干什么
wk enter lxslot1                   # 进去干活
```

**开始一件新事**

```bash
git clone <repo> /data/src/fix-bug     # 你自己准备代码
wk bind lxslot2 /data/src/fix-bug      # 绑进空的那个容器，服务自动起
wk enter lxslot2
```

**并发**就是绑不同代码到不同容器，互不干扰。

**从 Mac 直接进**

```bash
mosh --ssh="ssh -i ~/.ssh/id_rsa" root@203.0.113.10 -- wk enter lxslot1
```

**快在哪**：慢的部分（装 Docker、拉几十 G 镜像）在 `wk new` 时一次性付清。
之后绑代码是秒级（只是加个挂载），恢复冻结的容器也是秒级。唯一稍慢的是起项目服务。

## 11. 设计原则

1. **容器与代码解耦** —— 容器不持有代码，代码不感知容器。
2. **不自己存状态** —— 状态全在 LXD 里，没有第二份真相。
3. **幂等可重入** —— 造容器链路很长（装 Docker、灌镜像、播认证），中途失败是常态，重跑必须安全。
4. **冻结优先于关停** —— 回收资源不能以丢失工作状态为代价。
5. **显式安全边界** —— 容器是 privileged 的，属于**可信本地环境**，不是多租户隔离边界。
   这句话要写在 README 顶部。
6. **先诊断后动手** —— 环境问题（代理不通、权限不对、内存不够）由 `doctor` 和容量守卫在开工前拦下。

---

## 12. 演进方向

设计上留口，当前不做：

- **多 host**：CLI 里所有 `lxc` 调用过一层间接，将来把「在哪执行」换掉即可。
- **IDE 接入**：目前只能 `wk enter`；要接 VS Code Remote 需要给容器开端口。
- **自动挑容器**：容器少的时候人自己选就够；多了再加「挑一个空闲的」。
